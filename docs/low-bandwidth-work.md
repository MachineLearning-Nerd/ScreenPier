# Low-bandwidth development run

ScreenPier must keep the same Linux desktop usable when the route slows. The current fixed quality modes are the reference for comparison. Previous automatic bitrate selectors failed the 0.5 Mbps route-change test, so a new selector must first explain where old video waits.

## Evidence that sets the priority

An archived isolated cold-start Low data run at 0.5 Mbps, 200 ms added round-trip delay, and 2 percent random loss preserved exact native-pixel 14 px text OCR with no proxy queue drops. Its host readiness log nevertheless recorded 35 display-expiry falls and 13.8 seconds of unavailable control after first becoming ready during the roughly 49-second session; the longest completed gap was 1.6 seconds. The one-second browser samples showed only 3/18 Waiting observations during the constrained phase and 7/20 after restoration. Thus occasional samples and a readable screenshot are insufficient evidence of reliable input. The [sanitized readiness trace](../tests/fixtures/low-data-readiness.jsonl) and its [provenance](../tests/fixtures/low-data-readiness.provenance.json) reproduce the interruption counts with `python3 tools/readiness_summary.py tests/fixtures/low-data-readiness.jsonl`. The OCR and proxy findings remain in private receipts. These numbers describe one historical Linux Chromium fixture run, not the current candidate or Mac Comet.

The separate failed Smooth-to-Low run stalled for the full 15-second handover check and dropped 49 packets at the proxy. During its initial 5 Mbps Smooth phase, capture-to-encoder output was around 30–50 ms while acknowledged frames later became more than one second old. The first implementation unit orders lease retirement before the replacement offer. Candidate diagnostics now record the WebRTC send queue at regular samples and at readiness changes. Together with proxy and browser timing, those samples can locate where video waits; queue snapshots alone cannot distinguish network delay from browser playout delay. Neither correction has a measured performance gain yet.

On 14 October, a new cold-start Low data run used a complete 5 Mbps, 80 ms, zero-loss starting profile and then 0.5 Mbps, 200 ms added round-trip delay, and 2 percent loss. Current video appeared 1.36 seconds after the route change, and the mode stayed Low data for 18 seconds. The sender queue did not grow without bound, and the proxy recorded no queue drops. The browser sent a test click and `z`, but the Linux fixture received neither. The host recorded 30 changed-display expirations and about 10.77 seconds without input readiness after first becoming ready in its 34.6-second session. At these expirations, the acknowledged image was usually 500 to 502 ms old, the latest capture was about 70 to 140 ms old, and the sender queue was often empty. Capture to encoder output was 27 to 40 ms; browser acknowledgements in the constrained phase reported 336 to 856 ms of frame age, with a median of 358 ms across the one-second samples. The 500 ms changed-content gate correctly revoked input, but frequent revocation makes this route unusable for dependable typing. A follow-up Clear text run read back a zero-millisecond browser jitter-buffer target, which the app already requests, and still lost its final test key. It was not an A/B test. A matching Low data run stopped before the measured phase when another focus change hid its fixture. These observations are local runs of the current private binary, not Mac results or accepted fixes.

An isolated Low data 12 fps build kept the same 560 kbps cap and freshness deadlines. In one guarded 0.5 Mbps run it showed current video in 0.79 seconds but ended the constrained phase without input readiness; the host recorded 50 display-expiry falls and 18.69 seconds unavailable over the session. The current 8 fps build also failed a separate run, taking over five seconds to show current post-route video. An alternating comparison stopped when a Mac client connected to the private service, so these runs do not establish a cadence winner. The 12 fps source change was removed; the private service was never switched to it.

Five later guarded runs used the installed Actual size binary, whose video path still uses 560 kbps and 8 fps in Low data. All five showed current post-route video within 0.54 to 0.82 seconds, but only three completed all phases with the exact native `z` test. The 14 px native crop passed literal OCR in all phases that reached image capture. In one failure, the browser and host both reported input ready before a click and key were sent; the fixture received neither key transition. The host's acknowledged frame was already 447 ms old before the input, leaving at most 53 ms under the changed-content deadline. In another failure, input readiness was false when the constrained-phase test began. Across the five sessions, event-complete traces recorded 9 to 52 display-expiry falls and 3.49 to 13.11 seconds without input readiness after first becoming ready. These are synthetic Linux Chromium runs, not Mac Comet measurements. They confirm intermittent control failure despite moving video and some successful runs; they do not identify a proven faster capture cadence.

A frame-linked input prototype passed its Rust and browser unit tests but failed its first guarded 0.5 Mbps run. Current video appeared in 0.54 seconds after the route change. At the constrained input test, the browser sent a click, pointer, and `z`; the host admitted all five actions, but the Linux fixture received only the click. Actor counters showed two completed actions, one expired input, and a queue purge. The last ready-state trace gave the displayed changed frame about 116 ms of control lifetime. These counters do not identify which action expired, so admission must not be reported as delivery. The prototype was not installed. A separate 400 kbps cap screen used the installed binary and failed the initial current-video check even on the 5 Mbps starting route: browser frames advanced but the fixture's small changing tick remained unreadable for five seconds. It did not reach the constrained input or OCR checks. Neither candidate meets acceptance. A proposed 750 ms changed-content deadline was rejected in review because it would permit control of an outdated image for 250 ms longer; the original 500 ms deadline remains in source and the installed service.

A second guarded frame-linked run, rebuilt with the original 500 ms limit, showed current video in 0.98 seconds after the 0.5 Mbps route change but again lost `z`. Its acknowledged frame was already 449 ms old before the click. This time all five messages were denied at host admission, so the actor never received them. A separate 1 Mbps, 150 ms RTT, 1 percent loss input-latency screen on the installed binary lost its first `A` after the browser sent it; the physical field had focus and received the click. No latency percentile is valid from that failed run. These runs show both admission-time and post-admission input loss; one fixed client-side frame proof cannot solve both.

## Acceptance for this run

The primary local test starts with 5 Mbps, changes to 0.5 Mbps with 200 ms added round-trip delay and 2 percent random packet loss, then restores 5 Mbps. The test uses the physical 1920 by 1080 Hyprland output through an isolated host and browser. A candidate passes only if each of five runs shows current video within five seconds of the route change, exact native-pixel reading of the 14 px fixture text, no lost or duplicate input transitions, and no unbounded queue growth. Count every readiness fall and its duration from host events, including falls between browser samples. The test records presented frames, readiness, packet drops, transport statistics, host stage timings, and the binary hash. Alternate baseline and candidate runs. Report medians and ranges, including failures.

The separate 1 Mbps input test uses 150 ms added round-trip delay and 1 percent loss. It requires exact literal key delivery before reporting input-to-visible latency. Synthetic shaping does not include Tailscale overhead or prove Mac Comet performance. The final acceptance path remains the actual Mac browser and tailnet route in [validation](validation.md).

## Work sequence

1. Repair the isolated test scripts after the ScreenPier rename. Preserve the private service and create fresh receipts for the current release binary.
2. Measure fixed Low data from startup and Smooth-to-Low switching under the same route. Separate encoder output delay, sender packet timing, proxy queue time, and browser presentation delay.
3. Compare at least two designs against the measured bottleneck. Reject a design that depends on increasing the stale-display input deadline to hide delayed video.
4. Implement the smallest candidate that improves the measured path. Keep each code change and its behavioral check separate.
5. Repeat the full tests, inspect the exact built artifact, and document accepted and rejected results. Leave the installed private service unchanged until a separate deployment decision.

The first two steps are diagnostic. They can find that no candidate passes this run. A failed or incomplete run stays marked **NOT VERIFIED** or **INCONCLUSIVE**, rather than becoming a performance claim.

The next experimental candidate is the optional [native-pixel viewport](viewport-prototype.md). It is separate from the full-output baseline and must pass its coordinate, freshness, readability, and physical-input checks before any deployment decision.

The first five-pair viewport comparison on 14 October improved completion from 1/5 to 4/5 and made 12–16 px fixture text readable in each completed run, but it still rejected every action in one run when the displayed frame was 546 ms old. Even successful runs included gaps up to 1.40 seconds. Explicit native input outcomes expose this failure without replaying uncertain actions; they do not cure stale video. The next media-path experiment must reduce the age of the displayed image under packet loss, then repeat the same five-pair gate. Focus remains uninstalled and **NOT VERIFIED** at 0.5 Mbps / 2% loss.
